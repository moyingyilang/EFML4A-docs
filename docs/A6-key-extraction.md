# A6 · VFS 密钥是怎么找到的

**这篇讲什么**
`.blc` 的 ChaCha20 密钥（32 字节）是从哪来的、怎么验证它对不对。

**为什么重要**
逆向项目里最容易被「跳过」的一步就是「你怎么知道密钥是这个」。
这篇把三种方法都写清楚，包括为什么最终信任它。

**读完你会**
- ✅ 知道三种获取密钥的路径
- ✅ 能自己验证一个密钥对不对
- ✅ 理解「硬编码常量」和「机密」的区别

---

## 先说结论

```
密钥（32 字节）长这样:
  Base64: 6VsxesT4KFadI6hr8nHctT6Eb6dckk1nHbqOOPTKUuE=

这个值【不是秘密】，它是游戏二进制里的硬编码常量。
所有公开的终末地工具里都有它，已经存在好几年了。

三种获取方式:
  ① 从游戏二进制里搜（最直接）
  ② 从内存里挖（要 root）
  ③ 从公开参考实现里拿（最快）
```

---

## 1. 先搞清楚：这是「密钥」还是「常量」

**这两者区别很大：**

| | 密钥（secret） | 硬编码常量（constant） |
|---|---|---|
| 例子 | 服务器下发的会话密钥 | AES 的 SBox、这里这个 ChaCha20 key |
| 是否保密 | 必须 | 不需要 |
| 换个版本会不会变 | 通常会 | 通常不会 |

**这个 ChaCha20 密钥属于哪类？**

```
它是【硬编码常量】:
  · 打在游戏二进制里，所有用户一样
  · 从 1.1 版本到 1.6.4 都没变过
  · 公开工具（EndfieldStudio / AnimeStudio）里都有

⇒ 它属于【格式规范】，就像 zip 的魔数一样
```

**为什么这个区分重要？** 因为「拿到格式常量」和「破解加密」是两件事。
前者是做逆向的常规工作，后者才涉及攻防。

## 2. 方法一：从游戏二进制里搜（最直接）

### 2.1 找 base64 字符串

**密钥在代码里常常以 base64 形式存着**（因为方便写在配置里）：

```bash
# 在 libil2cpp.so 里搜 base64 字符串
strings libil2cpp.so | grep -E '^[A-Za-z0-9+/]{43}=$'
```

**为什么是 43 个字符 + 一个 `=`？**
32 字节的 base64 编码 = `ceil(32/3) × 4` = 44 个字符（末尾带 `=`）。

**如果你找到 `6VsxesT4KFadI6hr8nHctT6Eb6dckk1nHbqOOPTKUuE=`，就是它。**

### 2.2 找原始字节数组

**有时候密钥以原始字节形式存在：**

```bash
# 转成 hex 搜
# e9 5b 31 7a c4 f8 28 56 9d 23 a8 6b f2 71 dc b5 ...

# 在二进制里搜（用我写的 binsearch）
tools/.efml4a-bin/binsearch libil2cpp.so e95b317ac4f82856 8
```

**⚠️ 为什么可能搜不到？**

```
· 密钥可能被拆开存放（分几段）
· 可能被 XOR 过一层
· 可能在 global-metadata.dat 而不是 .so 里
· 可能被编译器优化成别的形式
```

**我实际是在 `global-metadata.dat`（74 MB）里找到的** ——
那是 il2cpp 的元数据文件，C# 层的字符串常量都在里面。

```bash
strings global-metadata.dat | grep -F '6VsxesT4KFadI6hr8nHctT6Eb'
```

## 3. 方法二：从内存里挖（要 root）

**如果静态搜不到，就等它被加载到内存再搜。**

### 3.1 思路

```
游戏启动 → 密钥被加载到堆/栈上
→ 用 /proc/<pid>/mem 扫描
→ 找到那 32 个字节
```

### 3.2 用 `ms` 工具

```bash
# 找游戏进程
PID=$(pidof com.hypergryph.endfield)

# 搜已知的密钥字节（如果你已经知道了）
su -c "tools/.efml4a-bin/ms $PID e95b317ac4f82856 8 8"

# 输出:
#   HIT addr=0x7a... (base=0x7a... +0x...)
#   scanned 7172.8MB hits=4
```

**性能：** 7 GB 内存扫一遍大约几秒（8 线程）。

### 3.3 如果完全不知道密钥怎么办

**那就得用「已知明文攻击」的思路：**

```
1. 找一个你能同时拿到明文和密文的片段
   · 比如 .blc 解密后开头是 `05 00 00 00`（version=5）
   · 而 .blc 的 [12..16) 是加密后的这 4 个字节
   ⇒ 明文、密文都有

2. 用这 4 个字节反推 keystream 的前 4 个字节
   keystream[0..4) = cipher[12..16) ^ plain[0..4)

3. 但 keystream 是 ChaCha20 输出的，反推不了密钥
   ⇒ 这条路走不通（ChaCha20 设计上就是抗已知明文攻击的）
```

**所以「已知明文攻击」对 ChaCha20 无效。**
**要么静态找到密钥，要么动态 hook 那个算 keystream 的函数。**

### 3.4 动态 hook 的思路（我没走这条路）

```
Hook ChaCha20 的初始化函数
⇒ 打印出它收到的 key 参数
⇒ 直接拿到密钥

需要: 定位 libil2cpp.so 里 ChaCha20 相关函数的地址
工具: zygisk payload 或 frida
```

## 5. ★ 最重要的一步：验证

**从公开来源拿到的密钥，你不能直接信 —— 得自己验。**

### 5.1 验证方法：CRC32

**`.blc` 的结构自带一个校验位：**

```
[0..12)     nonce
[12..len-4) ChaCha20 加密的 body
[len-4..len) CRC32(body[0..len-4))     ← 用这个验
```

**验证步骤：**

```bash
# 1. 用密钥解密 body
# 2. 计算解密后前 (len-4) 字节的 CRC32
# 3. 和文件末尾的 4 字节比对
```

**我的 `blcdump` 工具会自动做这件事：**

```bash
tools/.efml4a-bin/blcdump /path/to/0CE8FA57.blc

# 输出:
#   version=27123848 codeVersion=5
#   CRC32: 存储=0x5f83c3d2 实算=0x5f83c3d2 ✓    ← 这个 ✓ 就是验证通过
```

**如果密钥错了，CRC 一定对不上** —— 而且解出来的内容会是乱码。

### 5.2 验证方法：结构合理性

**即使 CRC 恰好撞上（概率极低），结构也会露馅：**

```
正确解密的 body:
  @0  u32 version = 5          ← 合理
  @8  u16 strLen  = 10
  @10 "InitBundle"             ← 可读字符串！

错误密钥解出来的:
  @0  u32 = 0x8A3F2C71          ← 不合理
  @10 一堆乱码
```

**「组名字段能不能读出来」是最直观的判断。**

## 6. 密钥的完整参数（容易漏的部分）

**光有密钥还不够，还得知道怎么用：**

```
密钥:    32 字节（就是上面那个 base64）
nonce:   .blc 文件的【前 12 字节】
counter: 从 1 开始  ← ⚠️ 最容易错的地方
范围:    [12, len-4)
```

**⚠️ counter 用 0 会怎样？**

```
密钥对，但解出来是乱码。
CRC 对不上，结构也不合理。
⇒ 你会以为密钥错了，其实只是 counter 错了。
```

**这个坑我踩过。**

---

## 7. 不同版本会不会变？

**实测：从 1.1 到 1.6.4，这个密钥没变过。**

**但这不代表以后不会变。** 如果游戏更新后你的工具突然失效，
**第一件事就是重新验证密钥**：

```bash
tools/.efml4a-bin/blcdump <新的.blc>
# 看 CRC 是否 ✓
# 如果 ✗ ⇒ 密钥变了，或者 nonce/counter 方式变了
```

## 8. 合规说明

**把密钥写进公开文档，合适吗？**

**我认为合适，理由：**

```
1. 它是【硬编码常量】，不是会话密钥
   → 所有用户一样，不涉及任何人的隐私

2. 它已经在公开的社区工具里存在多年
   → EndfieldStudio / AnimeStudio / 各种博客

3. 没有它就无法读写自己的游戏文件
   → 这和「破解 DRM」不是一回事，更像是「读懂文件格式」

4. 真正的保护在别处
   → 完整性校验、反篡改、服务端验证
   → 密钥只是「格式的一部分」
```

**类比：** 这就像公开 ZIP 格式的魔数 `50 4B 03 04`。
你不公开它，别人也能自己找到 —— 而且找到了也做不了坏事。

**我的做法：**
- 在文档里写清楚来源（[CREDITS.md](../CREDITS.md) 感谢 Harry Huang 等人）
- 不把它当成「破解成果」炫耀
- 同时强调合规边界（见 [SECURITY.md](../SECURITY.md)）

## 9. 踩坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| 解出来是乱码 | counter 用了 0 | 改成 1 |
| CRC 对不上 | 密钥错了，或 nonce 取错 | 确认取前 12 字节 |
| 结构不合理 | 密钥对了但偏移错了 | 检查 8 字节 tag（见 A1） |
| 静态搜不到密钥 | 被拆分/混淆 | 用内存扫描，或动态 hook |
