# C2 · 阻塞与失败记录

**这篇讲什么**
一个「看起来全对，但游戏就是不认」的真实案例。

**为什么值得读**
因为这里面有一件事，比任何成功的经验都更有价值：
**我用一个 A/B 实验，证明了游戏在跳过我的文件 —— 原因是一个字节。**

---

## 结论先行

```
游戏会静默跳过 compBI 被改动的 .ab。

什么意思？compBI 是「压缩后块信息有多大」这个字段。
我的压缩器比游戏的差一点点，导致压缩后多出 1 个字节。
游戏看到这个不符，就不加载这个资源了 —— 不报错，不崩溃，只是不用。
```

---

## 1. 怎么发现的（A/B 实验）

**当时的情况：** 我以为写入链路已经完全正确了 ——
文件长度不变、目标区验证通过、游戏也不崩溃。但纹理就是不显示。

**于是我做了个对照实验，只改一个变量：**

| | `.chk` 状态 | `vktex` 日志里有 `304×68` 吗 |
|---|---|---|
| **A** | 原始 | ✅ 有：`Copy #57 ext=304x68 data=fffffdfc` |
| **B** | 我改过的 | ❌ **完全没有** |

**两次都挂同样的 `vktex` payload，都等 20 秒抓日志。**

**⇒ 结论：游戏读到我的文件后，决定不用它。**

---

## 2. 为什么不用？追到一个字节

我把 `abpack` 的日志调出来对比：

```
原始 bundle (540d0269....ab, 9,806 字节):
  compBI   = 101          ← 「压缩后的块信息」占多少字节
  块0 comp = 9,646        ← 数据块压缩后多大

我改完之后:
  compBI   = 102          ← ⚠️ 变成 102 了
  块0 comp = 9,027        ← 数据块反而变小了
```

**这里有个反直觉的地方：数据块变小了（9,027 < 9,646），但块信息却变大了（102 > 101）。**

因为块信息里存的是「每块压缩后多大」这些数字。数字变了，
再用 LZ4Inv 压缩这串数字，压出来的长度不一定跟着变小 —— 这次就变大了。

**游戏要求 `compBI` 跟原来一模一样。多 1 字节都不行。**

---

## 3. 为什么 `pad` 模式救不了

我写 `abpack` 的时候想过这个问题，所以做了 `pad` 模式：

```
思路: 给【未压缩】的块信息后面追加填充字节，
     让它压缩后恰好等于原来的 compBI。

问题: 填充只会让压缩结果【变大或不变】，不会变小。
     新块信息本来就有 102 字节，
     无论加多少填充，都压不回 101。
```

**⇒ 数学上就做不到。`pad` 模式退化成 `min` 模式 + 零填充。**

## 4. 试过但不行的方法（别重复了）

| 方法 | 结果 | 为什么不行 |
|---|---|---|
| 改 `.ab` 内容 | ❌ | `compBI` 变了，游戏跳过 |
| 改 `.blc` 的 offset 指向别的资源 | ❌ | 游戏会重建 `.blc`，改回原样 |
| 指向一个尺寸不同的资源 | ❌ | GPU 直接 `SIGSEGV`（越界） |
| 指向一个尺寸相同的资源 | ⚠️ | 不崩了，但 `.blc` 还是被重建 |
| 直接改 `pref_main.json` | ❌ | 加密没破（试了 6 类方案） |
| 拦截 Temp 缓存 | ❌ | 缓存里根本没有纹理数据 |
| 拦截完整性校验 | ❌ | 不需要 —— 删清单就能绕过 |
| `streamOffset=0` | ❌ | 覆盖了 Unity 文件头，启动就退 |
| LZ4 零填充 | ❌ | `0x00` 是非法 token，解压器报错 |

**这张表是几轮实验换来的。如果你也在做类似的事，可以直接跳过这些。**

## 5. 那份加密清单，我没破开

游戏有四个清单文件 `index_*.json` / `pref_*.json`，base64 编码的。

**它们的特征：**
```
解码后的 magic: bc95dcd8bde198b6cedadb909ea3b6ee（13 字节共同前缀）
熵:            6.800 / 6.868 bit/byte
```

**熵 6.8 说明什么？** 如果是 AES / ChaCha20 这种强加密，熵应该接近 7.99。
6.8 说明它是「轻量混淆」或者「压缩」，不是硬加密。

**但试了 6 类方案，全部失败：**

```
✗ VFS 的 ChaCha20（前12B nonce / nonce=0 / 后12B nonce）× counter 0/1
✗ 单字节 XOR（256 个 key 全试）
✗ 已知明文攻击（假设开头是 {" / [{ / {"version / {"files 等 7 种）
✗ ChaCha20 key 前缀当重复密钥用（4/8/16/32 字节）
✗ zlib / gzip / raw deflate（原文、+13 偏移、解密后都试了）
✗ 在 .so 里搜 "pref_main"/"index_main" 字符串（il2cpp 字符串是混淆的）
```

**不过后来发现：不需要破它。** 删掉清单让游戏重建就行 ——
因为清单是**根据文件内容确定性生成**的（删了重建，md5 完全一样）。

## 6. 还剩三条路（我没走完）

### A. 劫持读取（推荐）

```
Hook 住 open / read / pread / mmap
当游戏读 .chk 的某个区间时，返回【另一个合法 .ab 的字节】

好处:
  · 磁盘文件永远保持原始 ⇒ 游戏怎么校验都是对的
  · 游戏重建 .blc 时，按它「读到的内容」算 ⇒ 前后一致
  · 无法被绕过（除非它绕过 libc）

基础已经有了: libefml4a_libcprobe.so（68KB，验证过能加载）
```

### B. 修好 vkinject

```
关键是要用 3 个 hook 串成一条链:
  vkMapMemory            → 记录 memory → host 指针
  vkBindBufferMemory     → 记录 buffer → memory + offset
  vkCmdCopyBufferToImage → 用映射表算出 host，写数据

我的 vk304.so 只做了第 3 个 ⇒ 拿不到 host 指针 ⇒ 写不进去
payload-vktex.c 里已经有完整的 3-hook 结构，可以直接改
```

### C. 让 `compBI` 恰好相等

```
LZ4Inv 的流可以在末尾追加「纯字面量 token」
⇒ 可以精确控制压缩后长度

如果能让新数据块压缩后【恰好等于】原始的 9,646 字节
⇒ 块信息内容不变 ⇒ compBI 保持 101
⇒ 完全等结构
```

## 7. 这篇的教训

**技术上的：**

```
1. 流偏移不是 0 —— 用错会覆盖文件头
2. LZ4 没有结束标记 —— 不能零填充
3. 工具「打印成功」不等于「真的成功」
   （我的 blcsetdata 曾经 fopen 失败没检查，静默生成了无效文件）
4. 截图验证不可靠（小窗 / 时序 / 合成层）
5. payload 加载后会自动 unmap，maps 里查不到 ≠ 没加载
```

**方法上的：**

```
1. ★ 一定要做 A/B 对照，只改一个变量
   否则你永远不知道是哪个改动导致的

2. ★ 用多种独立手段交叉验证
   截图 / 内存搜索 / payload 日志 / 崩溃记录 —— 至少两种对上再下结论

3. ★ 结论要标注证据强度
   「我推测」和「我实测」是两回事

4. ★ 早期结论可能被推翻，要保留纠正记录
   这个项目里我至少有 5 个结论后来被自己推翻了
```
