# A3 · 加密体系

**这篇讲什么**
游戏用了三种加密。这篇讲每种是干什么的、怎么解。

**为什么重要**
你不解密，看到的永远是乱码。而且其中一种有个反常识的性质 ——
**加密和解密是同一个操作**，搞不懂这一点会写很多多余的代码。

**读完你会**
- ✅ 知道三种加密分别保护什么
- ✅ 理解「对合加密」为什么能简化实现
- ✅ 知道一个差点让整个项目翻车的 ShiftRows 坑

---

## 先说结论

```
三层加密，各管一段:

  ① ChaCha20  → 保护整个 .blc（目录文件）
  ② VFSAES    → 保护 .ab 的头部和块表
  ③ HGCipher  → 保护 PCK 补丁文件

★ 关键性质: VFSAES 是【对合】的
   加密(x) == 解密(x)
   ⇒ 你只需要实现一个函数，不是两个
```

---

## 1. ChaCha20（保护 `.blc`）

**它保护什么？** 整个 `.blc` 的目录内容。

**怎么用？**

```
密钥: 32 字节，硬编码在游戏里
nonce: .blc 文件的【前 12 字节】
counter: 从 1 开始  ← ⚠️ 不是 0
范围: [12, len-4)
```

```c
const uint8_t KEY[32] = {
    0xe9, 0x5b, 0x31, 0x7a, 0xc4, 0xf8, 0x28, 0x56,
    0x9d, 0x23, 0xa8, 0x6b, 0xf2, 0x71, 0xdc, 0xb5,
    0x3e, 0x84, 0x6f, 0xa7, 0x5c, 0x92, 0x4d, 0x67,
    0x1d, 0xba, 0x8e, 0x38, 0xf4, 0xca, 0x52, 0xe1,
};

// 正确
chacha20_xor(body, len, KEY, nonce, /* counter = */ 1);

// ❌ 错误: counter = 0 ⇒ 解出来全是乱码
```

**⚠️ 我踩过的坑：** counter 用了 0，解出来一堆乱码，
以为是密钥错了，查了很久才发现是这个参数。

**为什么是 1 不是 0？** 不知道。可能是作者的习惯，也可能是为了避免
和某个全零块的 keystream 冲突。总之实测就是 1。

## 2. VFSAES（保护 `.ab` 内部）

**它保护什么？** `.ab` 的头部字段、块表、节点表。

### 2.1 参数

```
Key    = 3AF18C47B2096DEE5124907C18D3A462
IV     = C7125EA904DB3388F20E774965BA1C93
XORKey = 0xF19AB7752CDD0196
SBox   = 自定义 256 字节置换表（不是标准 AES 的 SBox）
```

**它是 AES 的变种** —— 用了 AES 的轮结构，但 SBox 是自定义的，
还额外加了一个 XORKey 的步骤。

### 2.2 ★★★ 对合性（这个性质很重要）

```
E(E(x)) == x

翻译成人话:
  用同一个函数连续做两次，就变回原文。
  所以「加密」和「解密」是【同一个操作】。
```

**为什么这很重要？**

```
普通加密:
  需要两个函数: encrypt() 和 decrypt()
  写错一个就全错

对合加密:
  只需要一个函数: vfs_decrypt_block()
  加密用它，解密也用它
  ⇒ 代码量减半，出错机会也减半
```

**怎么验证的？**

```bash
# 拿任意 256 字节，连续做两次
tools/.efml4a-bin/lz4invtest   # 内含相关路径
# 或者自己写个小测试:
#   buf → vfs_decrypt_block() → vfs_decrypt_block() → 应该等于原 buf
```

**这个性质是我在实现过程中偶然发现的。**
一开始我老老实实写了解密，然后想写加密时发现 ——
把同样的操作再做一遍就恢复了。省了不少事。

### 2.3 稀疏路径（数据 > 256 字节时）

**问题：** VFSAES 的块是 256 字节。如果数据比 256 字节长怎么办？

**游戏的解法很特别：只加密一部分。**

```
numBlocksFloor = len / 16
step = 256 / numBlocksFloor
if (numBlocksFloor > 256) step = 1

做法:
  从第 0、1、2... 个 16 字节块里各取 step 字节
  → 汇入一个 256 字节的缓冲
  → 对这个缓冲做完整 VFSAES
  → 再散回原来的位置
```

**翻译成人话：** 数据很长时，它从每 16 字节里挑几个字节，
凑成一个 256 字节的「样本」加密，然后放回去。

**为什么要这样？** 我猜是为了性能 —— 对大块数据做完整加密太慢，
抽样加密能达到「看起来是乱的」的效果。

### 2.4 ⚠️⚠️ ShiftRows 的坑（差点让项目翻车）

**AES 的 ShiftRows 步骤是「行移位」，实现时行列方向很容易搞反。**

```c
// ❌ 错误（我一开始写的，转置了）
s[c*4 + r] = t[c*4 + src];

// ✅ 正确
s[r*4 + c] = t[src*4 + c];
// 其中 src = (r + c) % 4
```

**症状是什么？**

```
用错误实现算 E(IV)，得到一串数字，和参考实现对不上。
但看起来「也像是随机的」，所以很容易以为「大概就是这样」。
```

**怎么发现的？**

我拿一个公开实现（EndfieldStudio 的 C# 版）做交叉验证：

```
期望: E(IV) = AC 00 BD CD 75 25 05 63 D0 4D 2E 08 07 91 3D 5E
实际: （完全不同的数字）
```

**差一个字节都不行。** 改成正确的行列方向之后，立刻对上了。

**教训：** 写加密算法时，**一定要有一个已知答案的测试向量**。
否则你写错了也不知道 —— 反正输出看起来都是「乱码」。

## 4. 密钥是怎么找到的

**这些密钥不是猜的，是从游戏二进制里挖出来的。**

方法是内存扫描：

```
1. 找到一段「已知明文 → 已知密文」的样本
2. 在游戏进程内存里搜索这个密钥的可能位置
3. 用 tools/vfs/ms 扫描（多线程 /proc/<pid>/mem）
```

```bash
# 搜索内存
su -c "../.efml4a-bin/ms <pid> <hex模式>"
```

**⚠️ 合规说明：** 这些密钥是游戏二进制里的**硬编码常量**，
属于**格式规范**而非机密。它们已经在公开的社区工具里出现多年。
本项目在 [CREDITS.md](../CREDITS.md) 里注明了出处。

## 5. 踩坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| ChaCha20 解出乱码 | counter 用了 0 | 改成 1 |
| VFSAES 结果对不上 | ShiftRows 行列反了 | `s[r*4+c] = t[src*4+c]` |
| 大块数据解密失败 | 没走稀疏路径 | 处理 `len > 256` 的情况 |
| .ab 头部解析出负数 | 忘了用对合解密 | 先 VFSAES 再解析 |
