# A2 · `.ab` 容器格式

**这篇讲什么**
那 9,806 字节的 `.ab` 文件，里面还套了一层混淆。这篇拆它。

**为什么重要**
你要改的东西（图、模型、脚本）都装在 `.ab` 里。
不改容器就改不了内容。

**读完你会**
- ✅ 知道 `.ab` 的三层结构是什么
- ✅ 能读懂 `abverify` 的输出
- ✅ 知道为什么改完内容会「大小不对」

**⚠️ 这篇是三篇格式文档里最难的。**
第一次读看不懂没关系，先把「三层结构」记住，细节可以回头查。

---

## 先说结论

```
.ab 的结构:

  ┌──────────────────────────────────────┐
  │ 48 字节头部（混淆）                  │  ← 6 个字段被成对打乱
  ├──────────────────────────────────────┤
  │ 压缩块信息                           │  ← 也被混淆 + 压缩
  ├──────────────────────────────────────┤
  │ 数据块                               │  ← 你的图/模型在这
  └──────────────────────────────────────┘

三个「起始位置」:
  头部          @0
  块信息        @48
  数据块        @48 + align16(compBI)     ← ★ compBI 决定数据从哪开始
```

## 2. 头部（48 字节）

### 2.1 前 8 字节：自校验

```
@0   u32 a
@4   u32 b
```

**`b` 是由 `a` 算出来的，验证关系：**

```
b == ((4*(a ^ 0x4A92F0CD)) & 0xFFFF0000)
   ^ ror32(a ^ 0x4A92F0CD, 14)
   ^ 0xD8B1E637
```

**为什么需要这个？** 我猜是给游戏做快速校验的 ——
读 8 字节就能判断「这文件像我家的吗」，不用全解析。

**实际用途：** 你解析时可以用它确认「我读对了吗」。

### 2.2 中间 32 字节：6 组混淆字段

**真实的 6 个值被打散成 12 个半字（2 字节）存起来：**

| 偏移 | 存的是 | 真实字段 |
|---|---|---|
| +0 | `cBI2` | compBI 的低 16 位 |
| +2 | `flags2` | |
| +4 | `encFlags` | |
| +6 | `size2` | |
| +14 | `flags1` | |
| +16 | `uBI1` | uncompBI 的低 16 位 |
| +24 | `uBI2` | |
| +32 | `size1` | |
| +38 | `cBI1` | compBI 的高 16 位 |

**为什么要打散？** 增加逆向难度。实际效果是：你不能直接读，必须知道配对关系。

### 2.3 还原公式

```
compBI   = ror32(((cBI1 ^ cBI2 ^ 0xA121) << 16) | cBI2, 18) ^ 0xF74324EE
uncompBI = ror32(((uBI1 ^ uBI2 ^ 0xA121) << 16) | uBI2, 18) ^ 0xF74324EE
size     = rol64(((size1 ^ size2 ^ 0xDAD76848) << 32) | size2, 14)
           ^ 0xA4F1A11747816520
flags    = flags1 ^ flags2 ^ 0xA7F49310
encFlags ^= flags2
```

**这几个常数（`0xA121`、`0xF74324EE`、`0xDAD76848`、`0xA4F1A11747816520`）
是怎么找到的？**

> 我是拿一个已知的 `.ab`，从 `abverify` 里读出正确的 `compBI`（比如 101），
> 然后反推：`101 = f(cBI1, cBI2)`。
> 试了几种组合（XOR 顺序、移位方向、旋转位数），
> 用多个不同的 `.ab` 交叉验证，最后所有值都能对上。
>
> 这一步花了挺久 —— 因为没有文档，只能暴力试。

### 2.4 写回公式（逆运算）

```c
// compBI 写回
x = rol32(compBI ^ 0xF74324EE, 18);
lo = x & 0xFFFF;
hi = ((x >> 16) & 0xFFFF) ^ lo ^ 0xA121;
write_u16_be(cBI2, lo);      // offset +0
write_u16_be(cBI1, hi);      // offset +38
```

## 3. 块表（压缩块信息）

### 3.1 块数

```
读 u32（小端）⇒ raw
encCount = bswap32(raw ^ 0x8A7BF723)
lo = encCount & 0xFFFF
hi = encCount >> 16
blocksCount = ror32(((lo ^ hi) << 16) | lo, 18) ^ 0x91CE0A4F
```

**⚠️ 注意 `bswap32`（字节序翻转） —— 这里是大端存的。**

**这是我最容易搞混的地方之一：**
`.blc` 里全是小端，但 `.ab` 的块表里有几处是大端。
混合字节序，所以每次都要确认清楚。

**写回：**

```c
x = rol32(blocksCount ^ 0x91CE0A4F, 18);
lo = x & 0xFFFF;
hi = ((x >> 16) & 0xFFFF) ^ lo;
encCount = (hi << 16) | lo;
raw = bswap32(encCount ^ 0x8A7BF723);
write_u32_le(raw);
```

### 3.2 每块 10 字节（大端）

```
a, b, c, encFlags(^0x9CD6), d
```

**解出来：**

```
flags  = c ^ rol16(((a0 ^ a1) << 8) | a0, 14) ^ 0x523F
uncomp = ror32(((a ^ c ^ 0xA121) << 16) | c, 18) ^ 0xF74324EE
comp   = ror32(((b ^ d ^ 0xA121) << 16) | d, 18) ^ 0xF74324EE
```

**这几个值是什么意思？**

| 字段 | 意思 |
|---|---|
| `comp` | 这块数据压缩后多大（在文件里占多少） |
| `uncomp` | 解压后多大（通常是 131,072 或最后一块的余数） |
| `flags` | 加密/压缩标志 |

**★ 这就是 `compBI` 的来源** ——
块表里所有 `comp` 值构成的那张表，被压缩后的长度就是 `compBI`。

### 3.3 encFlags 的写回（最绕的一个）

```c
xf  = ror16(flags ^ c ^ 0x523F, 14);
p0  = xf & 0xFF;
a1  = ((xf >> 8) & 0xFF) ^ p0;
ef  = ((a1 << 8) | p0) ^ 0x9CD6;
```

**为什么这么绕？** 因为它把两个各 8 位的值打包进了 16 位，
还做了 XOR 和旋转。逆运算要一步步拆。

## 4. 节点表

**结构类似但常数不同：**

```
nodesCount: 常数 0xE4C1D9F2（正向）/ 0x5DE50A6B（逆向）
每节点: a = be32 ^ 0x8E06A9F8, b, c, d, 名字, e

名字的每个字节 ^= (j ^ 0x97)     ← j 是该字节在名字里的位置
flags  = ror32(((a1 ^ a0) << 16) | a0, 18) ^ 0xF13927C4 ^ b
offset = rol64(((d ^ c ^ 0xDAD76848) << 32) | c, 14)
         ^ 0xA4F1A11747816520
```

**节点表是干什么的？** 记录内部资源路径 → 偏移的映射。
节点表本身也是压缩的，要解压才能读。

## 5. 数据块

### 5.1 位置

```
dataStart = 48 + align16(compBI)
```

**⚠️ 注意是 `align16`（向上取整到 16 的倍数），不是直接加。**

**为什么？** 对齐要求。我的理解是给 SIMD 或者内存映射用的。

**例子（实测）：**

```
原始 bundle:
  compBI = 101
  align16(101) = 112
  dataStart = 48 + 112 = 160

我改完之后:
  compBI = 102
  align16(102) = 112        ← 还是 112！
  dataStart = 48 + 112 = 160  ← dataStart 没变
```

**这是我 `pad` 模式的一个意外收获：**
只要 `compBI` 的变化不跨越 16 字节边界，`dataStart` 就不变。
所以某些情况下 `compBI` 可以变而布局仍然合法。

**但 —— 游戏不认。见 [C2](C2-blockers.md)。**

### 5.2 数据块的编码

```
每个数据块:
  1. 用 VFSAES 解密/加密（对合，同一个操作）
  2. 用 LZ4Inv 解压/压缩
  3. 解压后大小 = uncomp（通常是 131,072）
```

## 6. 一个完整的实例

**目标：`ui_main_menu_logo_icon` 所在的 bundle**

```bash
$ abverify bundle.ab

# 输出:
#   compBI=101 uncompBI=137
#   块信息明文=137 (期望 137)
#   blocksCount=1
#     块0: comp=9646 uncomp=24560 flags=5
#   块表结束 @14, dataStart=160
#   完整流=24560
```

**翻译成人话：**

```
· 压缩后的块信息 101 字节
· 未压缩的块信息 137 字节
· 只有 1 个数据块
· 这个块压缩后 9,646 字节，解压后 24,560 字节
· 数据从第 160 字节开始
· 整个流（解压后）24,560 字节
```

**为什么 `uncomp=24560` 而不是 131,072？**
因为这是**最后一块**，数据量不足一整块。

## 7. 自己验证

```bash
# 看结构
../.efml4a-bin/abtool bundle.ab
../.efml4a-bin/abverify bundle.ab

# 导出完整流（解压后）
../.efml4a-bin/abverify bundle.ab /tmp/stream.bin
ls -l /tmp/stream.bin
```

**如果 `abverify` 报「块信息明文 ≠ 期望值」，说明你解析错了。**
最常见的原因是头部解混淆的公式用错了。

## 8. 踩坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| 块信息明文是 -1 | 头部解混淆错了 | 检查 6 个字段的配对 |
| blocksCount 大得离谱 | 忘了 bswap32 | 块表里有大端 |
| dataStart 对不上 | 忘了 align16 | `48 + align16(compBI)` |
| 解压失败 | LZ4 变体用错 | 块信息用 LZ4，数据块用 LZ4Inv |
| 解出来是乱码 | 没先 VFSAES 解密 | 顺序：VFSAES → LZ4 |
