# A4 · 压缩体系

**这篇讲什么**
解密完之后，数据还是压缩的。这篇讲游戏用的两种 LZ4 变体，以及一个害我debug很久的坑。

**为什么重要**
你要改 `.ab`，就得能正确压缩新数据 —— 而且要压得跟游戏差不多大。
压得太大，游戏会跳过你的文件（见 [C2](C2-blockers.md)）。

**读完你会**
- ✅ 分清两种 LZ4 变体
- ✅ 知道为什么不能对压缩流做零填充
- ✅ 知道自己的压缩器和游戏差多少

---

## 先说结论

```
两种 LZ4 变体，不能混用:

  标准 LZ4   → 用在【块信息】上，offset 是【小端】
  LZ4Inv     → 用在【数据块】上，offset 是【大端】

★ 最大的坑: LZ4 没有结束标记
   ⇒ 你不能对压缩流做零填充
   ⇒ 因为 0x00 会被当成「litLen=0, matchLen=0」的 token
     然后去读 offset，读到 0，解压器直接报错
```

---

## 1. 为什么有两种

**游戏的代码里有两个不同的压缩实现。**

**我的猜测：** 不同模块由不同人/不同时期写的，
块信息用的是标准 LZ4，数据块用的是改过的版本。

**怎么区分？看 token 的位布局。**

### 标准 LZ4

```
token 是一个字节:
  ┌─────────┬─────────┐
  │ 高 4 位 │ 低 4 位 │
  │ literal │  match  │
  └─────────┴─────────┘

litLen  = token >> 4
matchLen= token & 0x0F

offset: 2 字节，小端
```

### LZ4Inv

```
token 也是一个字节，但位是交错的:

  ┌───┬───┬───┬───┬───┬───┬───┬───┐
  │ 7 │ 6 │ 5 │ 4 │ 3 │ 2 │ 1 │ 0 │
  └───┴───┴───┴───┴───┴───┴───┴───┘
    └─mlC高位─┘ └─litC高位─┘ └mlC低┘└litC低┘

litLen = val & 0b00110011
enc    = (val & 0b11001100) >> 2

offset: 2 字节，大端
```

**为什么要这样交错？** 增加逆向难度。
你按标准 LZ4 去解，解出来是乱的。

---

## 2. token 的完整编码（LZ4Inv）

```
token = (litC & 3)
      | ((mlC  & 3) << 2)
      | (((litC >> 2) & 3) << 4)
      | (((mlC  >> 2) & 3) << 6)
```

**扩展字节：**

```
如果 litC == 15:
  后面跟一串 255，直到某个 < 255 的字节，累加得到额外长度

如果 mlC == 15:
  同理
```

**这个 15 是硬编码的上限** —— 跟标准 LZ4 一样的设计。

---

## 3. ★★★ 最大的坑：LZ4 没有结束标记

**问题：** LZ4 的流在解压时，是「一直解到输出缓冲满了」为止。
**流本身没有「到此结束」的标记。**

**所以你不能随便填充。看看错误做法：**

```
❌ 错误做法 1: 对压缩流零填充
   压缩数据 + 0x00 0x00 0x00...
   ⇒ 0x00 被解析为 token
   ⇒ litLen = 0, matchLen = 0
   ⇒ 去读 offset，读到 0
   ⇒ 解压器: 「offset = 0 是非法的」⇒ 报错

❌ 错误做法 2: 对未压缩数据填充
   你的数据 + 一堆 0x00
   ⇒ 压缩后长度变了
   ⇒ 解压后大小变了
   ⇒ 超出 uncompBI（块表里记录的「解压后多大」）
   ⇒ 游戏拒收

✅ 正确做法: 迭代搜索填充量
   给【未压缩】数据追加一点填充
   → 重新压缩
   → 检查压缩后长度是否恰好等于目标
   → 不等就调整填充量，再来一次
```

**这件事我在 `abpack` 的 `pad` 模式里实现了。**

---

## 4. `pad` 模式的算法

**目标：** 让新块信息压缩后的大小，恰好等于原来的 `compBI`。

```
输入: 新块信息（未压缩）、目标大小 target
输出: 填充后的块信息 + 填充量

算法:
  1. 压缩新块信息，得到 cLen
  2. 如果 cLen > target ⇒ 做不到，退回 min 模式
  3. 如果 cLen == target ⇒ 完美，直接用
  4. 如果 cLen < target ⇒ 需要填充:
       试 padLen = 1, 2, 3, ...
       每次: 原数据 + padLen 个字节 → 压缩 → 看是否 == target
       找到就停
```

**为什么填充量要「试」？** 因为 LZ4 的行为不是线性的 ——
多一个字节，压缩后可能变大 1、2、0 字节。没法算，只能试。

**⚠️ 但有失效的时候：**

```
如果新块信息本身压缩后就已经超过 target
⇒ 填充只会让它更大
⇒ 数学上做不到
⇒ 这就是我卡住的地方（见 C2）
```

## 5. 自研压缩器的演进

**为什么不直接用标准 LZ4 库？** 因为 LZ4Inv 是变种，标准库不认。

**所以我得自己写压缩器。写了四版：**

| 版本 | HBITS | CHAIN | lazy | 输出 | 相对游戏 | 耗时 |
|---|---|---|---|---|---|---|
| 游戏 | — | — | — | 122,604 (11.69%) | — | — |
| v3 | 17 | 16 | ✗ | 186,506 (17.78%) | **+52.1%** | ~10ms |
| v4 | 20 | 64 | ✓ | 152,915 (14.58%) | +24.7% | ~200ms |
| v4 | 22 | 256 | ✓ | 134,244 (12.80%) | +9.5% | ~500ms |
| v4 | 22 | 512 | ✓ | 127,087 (12.12%) | +3.7% | ~940ms |
| **v4** | **22** | **1024** | **✓** | **124,038 (11.83%)** | **+1.2%** | **~1850ms** |

**测试数据：** 一张真实 ASTC 纹理，1,048,576 字节

**v4 做了五个改进：**

```
1. 哈希表从 131k 扩到 1M 桶（HBITS 17 → 20）
2. 每条链的候选数从 16 加到 1024（CHAIN）
3. 匹配搜索改成「最近优先」（从链尾往前找）
4. 加快速排除：先比 src[ref+bestLen] 一个字节，不对就跳过
5. 加 lazy matching：如果下一个位置有更长的匹配，就跳过当前
```

**结果：从差 52% 追到差 1.2%。**

## 6. ⚠️ 但小数据上还是不如游戏

**这是个反直觉的发现：**

```
ui_main_menu_logo_icon (9,792 字节):
  游戏: comp = 9,646
  v4:   comp = 10,109    ← 比游戏大 4.8%

为什么？小数据上，压缩器的「初始开销」占比大。
      游戏可能用了更聪明的 match 策略，或者做了多次尝试。
```

**这 4.8% 就是 `compBI` 从 101 变 102 的直接原因。**
**也是游戏跳过我的文件的直接原因。**

**改进方向（如果继续做）：**
- CHAIN 加到 2048 / 4096
- 实现 optimal parsing（多次尝试选最优）
- 或者对小块数据单独优化

## 8. 踩坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| 解压返回 -1 | 对压缩流做了零填充 | 用 `pad` 模式迭代填充 |
| 解压后大小不对 | 填充了未压缩数据 | 保持 `uncomp` 不变 |
| 解出来是乱码 | LZ4 / LZ4Inv 用错 | 块信息 LZ4，数据块 LZ4Inv |
| offset 明显不对 | 字节序搞错 | LZ4 小端，LZ4Inv 大端 |
| 压缩后比原文件大 | 压缩器弱 | 调 CHAIN，或接受（游戏可能跳过） |
