# F1 · 历史与已证伪路线

**这篇讲什么**
这个项目走过的三条路，和其中两条是怎么死的。

**为什么值得读**
因为弯路比直路更有信息量。你会看到：
- 一个技术上可行的方案，是怎么被反篡改机制拖死的
- 一个「大家都说能行」的路，在新的 Android 版本上是怎么完全不通的
- 以及我自己推翻过的 5 个结论

## 三条路的演进

```
第一阶段  Vulkan 隐式层
          ↓  Android 17 上根本不通，五条路径全部穷尽
第二阶段  运行时 hook（Zygisk + Vulkan）
          ↓  成功过！但被反篡改看门狗拖死（9 次崩溃）
第三阶段  AssetBundle 离线修改  ← 现在这里
          ↓  格式全破了，写入也对了，但游戏跳过改动过的文件
```

---

## 第一阶段：Vulkan 隐式层（已证伪）

**想法很简单：** Vulkan 有个「隐式层」机制，可以往游戏和驱动中间插一层，
直接在 GPU 层面替换顶点/纹理数据。这样完全不用碰游戏文件。

**为什么不行：**

```
Android 17 的 user 构建对隐式层的限制:
  · 层搜索路径被收紧
  · 环境变量在 app 启动时被清空
  · 五条注入路径全部穷尽，都不通

⇒ 该路线放弃
```

**教训：** 「文档上写支持」和「实际能在生产设备上跑」是两件事。
Android 每个大版本都在收紧这类机制。

---

## 第二阶段：运行时 hook（曾成功，但被拖死）

**这是最有意思的一段。** 因为**它真的成功过**。

### 成功的部分

```
我把 vkCmdCopyBufferToImage 这个函数 hook 掉了。

作用: 游戏每次要往 GPU 上传纹理时，都会调用它。
     我可以在这个时刻，把要上传的数据换掉。

结果: 成功把 mod 的 262,144 字节 BC7 数据
     写进了游戏的 512×512 纹理
     命中 4 次，未映射 0 次
```

### 一个关键技巧

```
问题: vkMapMemory 的函数序言里有 CBZ 指令，无法 inline hook

解法: 改为 hook vkBindBufferMemory（这个好 hook）
     ⇒ 记录 buffer → memory 的映射关系
     ⇒ 然后【主动调用】vkMapMemory 去拿 host 指针
     ⇒ 拿到指针就能写数据了

这个技巧在 docs/E1 里还有用（vkinject 就靠它）
```

### 怎么死的

```
游戏有【反篡改看门狗】
⇒ 会周期性检查自己的代码段
⇒ 发现被改了 ⇒ 还原
⇒ 我的 hook 被反复拔掉

代价: 9 次崩溃（每次都是 SIGSEGV in UnityGfxDeviceW）
⇒ 战略转向离线改数据
```

**教训：** 运行时 hook 在「有反篡改的游戏」上，是打地鼠游戏。
能做，但成本极高，而且用户每次玩都得挂着 payload。

## 第三阶段：离线修改（当前）

**思路：** 不碰运行中的进程，直接改磁盘上的资源文件。

**已经做到的：**

```
✅ 格式 100% 逆向
✅ 工具能正确读写
✅ 写入链路字节级验证通过
✅ 游戏接受修改（不报错、不崩溃）
❌ 但游戏在加载时跳过改动过的 .ab
```

**为什么失败：** 见 [C2](C2-blockers.md) —— 一个字节的问题。

## 我推翻过的结论（重要）

**这些是我一开始以为对、后来被实验推翻的：**

| 我原来的结论 | 实际是什么 | 什么时候发现的 |
|---|---|---|
| 「启动只加载 InitBundle」 | 半对 —— 非音频资源只来自 InitBundle，但音频组也加载 | 第 16 轮（采样跑满 60 秒才发现） |
| 「启动加载多个组，纹理可能在别的组」 | 错 —— 其他组全是音频 | 第 16 轮（解出组名才明白） |
| 「`.blc` 重定向持久有效」 | 错 —— 游戏会重建 `.blc`，改回原样 | 第 20 轮（检查得太早，误判了） |
| 「改 `.chk` 后纹理上屏了」 | 存疑 —— 后来用内存验证没能复现 | 第 21 轮 |
| 「Temp 缓存拦截了 mod」 | 错 —— 缓存里没有纹理数据 | 第 20 轮（binsearch 全扫 0 命中） |
| 「`maps` 里没有 efml4a 就是 payload 没加载」 | 错 —— payload init 后会自动 unmap | 第 22 轮（看日志才发现它一直在工作） |
| 「`streamOffset=0` 可以用」 | 错 —— 流式 bundle 必须用 SerializedFile 大小 | 第 12 轮（这是最大的坑） |

**这张表是我最想让人看到的东西。**
因为写「我发现了什么」很容易，写「我以为对但错了什么」才能帮到别人。

## 技术教训（血泪版）

```
1. ★ 流偏移 ≠ 0
   用错会覆盖 Unity 文件头 ⇒ 启动闪退或花屏
   查了很久才发现问题不在写入链路，在「打哪里」

2. ★ LZ4 没有结束标记
   对压缩流零填充 ⇒ 0x00 是非法 token（offset=0）⇒ 解压器报错
   正确做法: 填充【未压缩】数据，然后迭代搜索填充量

3. ★ 工具「打印成功」不等于「真的成功」
   我的 blcsetdata 曾经 fopen 失败没检查 NULL，
   静默生成了一个无效的 .blc，然后我拿着它去写游戏……
   现在所有 fopen 都检查，所有 fwrite 都验证返回值

4. ★ 截图不可靠
   小窗 / 时序 / 合成层 / 短暂的显示窗口 —— 都可能让你看错
   改用: vktex 日志 + 内存搜索

5. ★ zygisk-loader 的 target.json 是对象数组
   不是 ["com.hypergryph.endfield"]
   而是 [{"app": "com.hypergryph.endfield", "lib": "<绝对路径>.so"}]
   这一个格式错误卡了我好几轮

6. ★ payload 加载后会自动 unmap
   /proc/<pid>/maps 里查不到 ≠ 没加载
   正确的判断: 看日志文件有没有生成
```

## 方法教训（更重要）

```
1. ★ 一定要做 A/B 对照，只改一个变量
   我最大的突破（发现游戏跳过文件）就是来自一次干净的 A/B

2. ★ 用多种独立手段交叉验证
   截图 / 内存搜索 / payload 日志 / 崩溃记录
   至少两种对上，才敢下结论

3. ★ 结论要标注证据强度
   「我推测」和「我实测」差得很远
   这个项目里我至少 5 个「我推测」后来被推翻了

4. ★ 早期结论可能被推翻 —— 保留纠正记录
   不要偷偷改掉旧文档，要写清楚「我之前以为是 X，实际是 Y」

5. ★ 先做控制实验，再动手
   比如「删清单会不会本身有害」
   这种东西 5 分钟能验，但能省掉几小时的误判
```
