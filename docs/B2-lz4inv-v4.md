# B2 · LZ4Inv v4 压缩器

**这篇讲什么**
我怎么把一个「比游戏差 52%」的压缩器，一点点追到「只差 1.2%」。

**为什么重要**
这是这个项目里少有的「纯工程优化」故事 ——
没有逆向的神秘感，就是调参数、加技巧、一步步逼近。

**读完你会**
- ✅ 知道 LZ4 类压缩器的调优手段
- ✅ 理解「为什么参数加码能提升压缩率」
- ✅ 知道优化到什么程度就够了（以及什么时候不够）

---

## 先说结论

```
从差 52.1% 追到差 1.2%，靠的是五个改动:

  1. 哈希表从 131k 扩到 1M 桶
  2. 每条链的候选数从 16 加到 1024
  3. 匹配搜索改成「最近优先」
  4. 加快速排除（先比一个字节）
  5. 加 lazy matching（延迟一步决策）

代价: 从 10ms 涨到 1850ms（慢 185 倍）
```

---

## 1. 起点：v3 有多差

**测试数据：** 一张真实 ASTC 纹理，1,048,576 字节

```
游戏原始:  122,604 字节  (11.69%)
v3:        186,506 字节  (17.78%)

⇒ 比游戏大 52.1%
```

**为什么差这么多？** 因为 v3 的搜索策略太保守：

```
HBITS = 17  ⇒ 只有 131,072 个哈希桶
CHAIN = 16  ⇒ 每个桶只记最近 16 个位置
没有 lazy matching
```

**翻译成人话：** 它在找「重复片段」时，只看最近 16 次出现过的地方。
如果某个片段很久没出现，它就找不到了。

---

## 2. 改动一：扩大哈希表

```
HBITS: 17 → 20
桶数:  131,072 → 1,048,576
```

**为什么有用？**

哈希表的作用是「记录某个 4 字节序列上次出现在哪」。
桶越多，碰撞越少，能找到的匹配越多。

**效果：** 152,915 字节（差 24.7%）

**耗时：** 10ms → 200ms

---

## 3. 改动二：加长链

```
CHAIN: 16 → 64 → 128 → 256 → 512 → 1024
```

**这是什么意思？** 每个哈希桶里存最近 N 个位置。
N 越大，能找到的匹配越多（但搜索也越慢）。

**效果表：**

| CHAIN | 输出 | 相对游戏 | 耗时 |
|---|---|---|---|
| 16 | 186,506 | +52.1% | 10ms |
| 64 | 152,915 | +24.7% | 200ms |
| 128 | 142,763 | +16.4% | 300ms |
| 256 | 134,244 | +9.5% | 500ms |
| 512 | 127,087 | +3.7% | 940ms |
| **1024** | **124,038** | **+1.2%** | **1850ms** |

**注意看这个趋势：** 每翻一倍，收益递减。
从 512 到 1024，只多拿了 2.5 个百分点，但耗时翻倍。

**为什么选 1024？** 因为 1850ms 对于「一次性构建」来说可以接受。
如果你要频繁压缩，用 256 更划算。

---

## 4. 改动三：最近优先

**原来的搜索顺序：** 从链头（最旧）往链尾（最新）找。

**改成：** 从链尾（最新）往链头找。

**为什么？**

```
LZ4 的 offset 是 16 位 ⇒ 最大 65535 字节
⇒ 太远的匹配用不了

先找最近的，通常更快找到「够长且距离合法」的匹配
```

**效果：** 主要是速度提升，压缩率差不多。

---

## 5. 改动四：快速排除

**原来的比较：**

```c
// 对每个候选，从头开始逐字节比较
long ml = 0;
while (ml < maxL && src[ref + ml] == src[ip + ml]) ml++;
```

**问题：** 如果这个候选明显不行（比如第一个字节就不匹配），
也要走一遍循环。

**改成：**

```c
// 先比一个字节，不对就跳过
if (src[ref + bestLen] != src[ip + bestLen]) continue;
```

**为什么比 `bestLen` 位置而不是位置 0？**

假设当前最佳匹配长度是 10。那任何「长度 ≤ 10」的候选都没意义。
所以先比第 10 个字节 —— 如果连它都不对，这个候选肯定不超过 10。

**这是个小技巧，但效果显著。**

---

## 6. 改动五：lazy matching

**这是最能提升压缩率的一个改动。**

**原来的逻辑（贪心）：**

```
在位置 i 找到一个长度 8 的匹配
⇒ 立刻用它
⇒ 跳到 i+8 继续
```

**问题：** 也许位置 i+1 有个长度 20 的匹配，但你已经在 i 处用掉了。

**lazy matching（懒惰匹配）：**

```
在位置 i 找到长度 8 的匹配
⇒ 先不急着用
⇒ 看看 i+1 有没有更长的
   · 如果有（比如长度 20）⇒ 放弃当前位置，跳到 i+1
   · 如果没有 ⇒ 用当前位置的匹配
```

**代码长这样：**

```c
long len1 = find(src, ip, ...);
if (len1 >= 4 && ip + 1 + 12 < n) {
    long len2 = find(src, ip + 1, ...);
    if (len2 > len1 + 1) {   // 下一个明显更好
        ip++;                 // 跳过当前位置
        continue;
    }
}
// 用当前位置的匹配
```

**为什么是 `len2 > len1 + 1`？**
因为你放弃长度为 `len1` 的匹配，去拿长度为 `len2` 的，
至少要多赚 1 个字节才划算（否则多了个 literal，没净收益）。

**效果：** 这是从 24.7% 追到 9.5% 的关键之一。

---

## 7. 完整参数

```c
#ifndef HBITS
#define HBITS  20        // 1M 哈希桶
#endif
#ifndef CHAIN
#define CHAIN  1024      // 每条链 1024 个候选
#endif
```

**可以编译时覆盖：**

```bash
# 默认（最高压缩率）
clang -O2 -o lz4invcomp4 lz4invcomp4.c

# 快速模式（CHAIN=256，压缩率低一点点，速度快 4 倍）
clang -O2 -DCHAIN=256 -o lz4invcomp4f lz4invcomp4.c
```

## 9. 多数据点（看看不同数据上的表现）

| 数据 | 大小 | v4 输出 | 占比 |
|---|---|---|---|
| 真实 ASTC 纹理 | 1,048,576 | 124,038 | 11.83% |
| 纯品红 ASTC_4x4 | 1,048,576 | 4,127 | **0.39%** |
| 棋盘图案 ASTC_6x6 | 9,792 | 10,109 | **103%** ⚠️ |

**注意第三行：** 小数据上，v4 的输出比输入还大 ——
因为压缩后的元数据开销超过了压缩收益。

**而游戏的 9,646 字节说明它处理得更好。**
**这就是我卡住的地方。**

## 10. 什么时候「差 1.2%」还不够

**这个项目就是活例子。**

```
1,048,576 字节的纹理: v4 只比游戏大 1.2% ⇒ 够用
9,792 字节的纹理:     v4 比游戏大 4.8% ⇒ 不够用

为什么？因为小数据上，相对误差被放大。
而且游戏对 compBI 的要求是【完全相等】，不是「差不多」。
```

**所以「优化到 1.2%」在某种意义上是个假胜利** ——
真正的判据是「能否恰好等于目标大小」，而不是「平均差多少」。

**这是我从这件事学到的：**
优化指标要选对。我一直在看「平均压缩率」，
但真正重要的是「能否精确匹配」。

## 10.5 踩坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| 压缩后比游戏大很多 | CHAIN 太小 | 调到 256/512/1024 |
| 压缩速度太慢 | CHAIN 太大 | 降到 256（压缩率只低一点） |
| 解压回来不一致 | token 位布局写错 | 对照 A4 的位布局图 |
| 小数据上反而变大 | 压缩器初始开销占比大 | 这是已知限制，见第 10 节 |
