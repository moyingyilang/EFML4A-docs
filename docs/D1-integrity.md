# D1 · 完整性机制

**这篇讲什么**
游戏怎么知道自己的文件被改了？我又是怎么绕过、以及为什么绕过之后还是不行。

**为什么重要**
这是「为什么游戏不认我改的文件」这个问题的一半答案。
另一半在 [C2](C2-blockers.md)。

**读完你会**
- ✅ 知道游戏用哪四个文件做校验
- ✅ 知道这些清单是「确定性生成」的（这是个重要性质）
- ✅ 知道为什么删清单能绕过、但绕过之后还是失败

---

## 先说结论

```
游戏用四个 json 文件做完整性清单:
  index_initial.json / pref_initial.json
  index_main.json    / pref_main.json

★ 这些清单是【确定性生成】的:
   删掉 → 启动 → 游戏重建 → md5 完全相同
   ⇒ 它根据文件内容算出来的，不是签名

★ 所以「删清单」能绕过校验。
   但绕过校验 ≠ 文件被接受（见 C2）。
```

---

## 1. 四个清单文件

```
/data/media/0/Android/data/com.hypergryph.endfield/files/
  index_initial.json    3,172 字节（base64 编码后）
  pref_initial.json     2,716
  index_main.json     286,020
  pref_main.json      273,556
```

**它们是什么？** 我的理解是「资源索引 + 校验信息」。
`initial` 对应启动包，`main` 对应主资源包。

---

## 2. 它们是加密的（但我没破开）

**解码后的特征：**

```
Base64 解码后:
  index_initial / pref_initial:
    magic = bc95dcd8bde198b6cedadb909ea3b6ee
  index_main / pref_main:
    magic = bc95dcd8bde198b6cedadb909e95a5e5
                                  ↑
                        前 13 字节相同

熵: 6.800 / 6.868 bit/byte
```

**熵 6.8 说明什么？**

```
如果是强加密（AES / ChaCha20）:  熵应该接近 7.99
如果是普通压缩（zlib）:          熵 7.5-7.9
如果是明文:                      熵 4-5

6.8 ⇒ 介于「压缩」和「混淆」之间
⇒ 是轻量混淆，不是硬加密
```

**我试了 6 类方案，全部失败：**

| 方案 | 结果 |
|---|---|
| VFS 的 ChaCha20（三种 nonce 方案 × 两种 counter） | ✗ 乱码 |
| 单字节 XOR（256 个 key 全试） | ✗ 无可读文本 |
| 已知明文攻击（7 种 JSON 开头假设） | ✗ 密钥解不出可读文本 |
| ChaCha20 key 前缀当重复密钥 | ✗ 可打印率仅 48-76/200 |
| zlib / gzip / raw deflate | ✗ 头不对 |
| 在 `.so` 里搜 `pref_main` / `index_main` 字符串 | ✗ il2cpp 字符串是混淆的 |

**⇒ 要破它，需要逆向 `libil2cpp.so` 的解密函数，或者动态 hook。**

---

## 3. ★ 但我不需要破它

**因为清单是确定性生成的。**

**实验：**

```
① 记录 index_main.json 的 md5 = 4296336e47c8a9b6...
② 删除所有清单
③ 启动游戏
④ 游戏重建 index_main.json
⑤ md5 = 4296336e47c8a9b6...   ★ 完全相同
```

**这意味着什么？**

```
游戏不是在验证「文件有没有被改」
它是在【扫描当前文件，算出清单，然后用自己的清单比对】

所以:
  删掉清单 ⇒ 游戏重新扫描 ⇒ 生成匹配当前文件的清单
  ⇒ 校验自然通过
```

**这是个设计缺陷** —— 校验数据存在本地，而且能重新生成。

---

## 4. `​.blc` 也会被重建（这是另一个发现）

**时间戳证据：**

```
我写 .chk:    10:44:49
游戏写 .blc:  10:45:15   （26 秒后）

游戏写入的 contentMD5 = 91e6e5e0201b29ba81689cdf134a50c5
实际 .chk 的 md5     = e83d71f2eba31d9f90e369612b4de9a4
⇒ 不匹配！

说明游戏的 contentMD5 【不是简单的文件 md5】。
可能是「对解密后的内容算 md5」，或者别的算法。
```

**这件事的后果：**

```
游戏会重建 .blc ⇒ 你在 .blc 里做的改动（比如重定向）会被覆盖
```

**我试过用 `.blcredirect` 把一个资源指向另一个：**

```
写入: off=720694（重定向到另一个纹理）
重建: off=312244（改回原始值）
```

**⇒ 重定向不持久。**

## 5. 启动加载行为（实测）

**`/proc/<pid>/fd` 跑满 60 秒的结果：**

| 组 | 组名 | `.chk` 数 | 大小 | 启动加载 |
|---|---|---|---|---|
| `0CE8FA57` | **InitBundle** | 1 | 208 MB | ✅ **唯一的非音频组** |
| `24ED34CF` | Audio | 4 | 3.6 GB | ✅ |
| `E1E7D7CE` | AudioChinese | 2 | 1.3 GB | ✅ |
| `F151B649` | HotfixAudio | 4 | 6.8 MB | ✅ |
| `7064D8E2` | Bundle | 28 | **16 GB** | ❌ 进场景才加载 |

**⚠️ 这里有个我踩过的坑：**

```
只看启动后 9 秒 ⇒ 看到 1 个 .chk ⇒ 以为「只加载 InitBundle」
跑满 60 秒再看   ⇒ 看到 11 个   ⇒ 才知道还有 3 个音频组

采样太早会得出错误结论。
```

## 6. Temp 缓存（我怀疑过，但排除了）

**每次启动，`files/Temp/` 会生成 4 个临时文件：**

| 文件 | 大小 | magic |
|---|---|---|
| `57948e64-...` | 472,714 | `e8 06 01 00` |
| `a8115b10-...` | 156,991,277 | **`11 ff 11 ff`** + UTF-16 UUID |
| `c11595c0-...` | 3,749,452 | `31 10 27 00` |
| `f8fa5579-...` | 170,988,312 | `68 9d 3d 01` |

**`11ff11ff` 格式解析：**

```
@0  u32 magic = 0x11ff11ff
@4  u32 = 36（UTF-16 字符数）
@8  UTF-16LE 字符串 "2954fa80-23c1-1579-2b22-4ecf..."
```

**我当时怀疑：这些缓存会不会拦截了我的 mod？**

**于是用 `binsearch` 全扫：**

| 搜索目标 | 157MB | 171MB | 473KB |
|---|---|---|---|
| 原纹理 ASTC `fcfdffff...` | 0 | 0 | 0 |
| `.ab` 头 `d7a1fddf983792` | 0 | 0 | 0 |
| `UnityFS` / `CAB-` | 0 | 0 | 0 |

**⇒ 里面没有纹理数据 ⇒ 不是 mod 加载的拦截者。**

**结论：这些是加密/压缩的更新包，和我们的 VFS 修改无关。**

## 7. 所以校验到底拦不拦 mod？

**答案：不拦。**

```
我改了 .chk + 更新了 .blc + 删了清单
⇒ 游戏正常启动、不报错、不崩溃
⇒ 校验没拦我
```

**真正拦我的是别的东西** ——
游戏在加载 `.ab` 时发现结构不对（`compBI` 变了），**静默跳过**。

**⇒ 详见 [C2 · 阻塞与失败记录](C2-blockers.md)。**

## 8. 踩坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| 报「检查完整性发现异常」 | 清单和文件不匹配 | 删清单让游戏重建 |
| `.blc` 改动被还原 | 游戏会重建 `.blc` | 只能靠运行时劫持 |
| 以为只加载 InitBundle | 采样太早 | 等 60 秒再看 |
| 怀疑 Temp 缓存拦截 | 里面没纹理 | 已排除 |
